### Added

- Host benchmark + A/B harness: per-variant latency, `.pte` size, and eager↔`.pte` parity, with artifacts under `docs/benchmarks/`. `e833db0`
- Host INT8 export path (PT2E + XNNPACK): on the base-width net the `.pte` shrinks ~2.9x (97.9 KB → 33.8 KB), recorded as an A/B row in `docs/benchmarks/`. `82ece14`
- Trained width A/B experiment measuring real validation accuracy against size; recommends the smallest `tiny` `(4, 8, 16)` width (~1,549 params, ~12.9 KB `.pte`), ~7.5x smaller than base at no accuracy loss. `96f0128`
- Host stress-detector oracle in Python — a golden spec of the on-device decision loop (EMA + dual-threshold hysteresis), testable off-device and usable for tuning. `dcbab7e`
- Detector tuning A/B harness sweeping threshold/EMA knobs (accuracy vs. flicker); recommends stress=0.55, release=0.35, alpha=1.0 with artifacts in `docs/benchmarks/detector_tuning.*`. `5e57faf`
- Noise-robustness sweep (accuracy vs. SNR) with an operating-floor report; the clean-trained model is accurate at high SNR but falls toward chance by 10 dB (floor 20 dB). `2fa5b7a`
- Auto-generated benchmarks index (`docs/benchmarks/README.md`) that rolls every benchmark JSON artifact into one legible page, defensive against missing/malformed records. `34b8d61`
- End-to-end Quickstart regression test certifying the documented train → export → run path on a clean checkout, with `.pte`↔eager parity to 1e-4. `78dfaed`
- Production recipe (`model/production.py`): builds the smallest robust StressNet `(4, 8, 16)` with noise-augmented training, exports a ~12.9 KB `.pte`, and records the evidence in `docs/benchmarks/production.{json,md}`. Non-destructive — only writes a `.pte` when `--out` is given. `b8cb16d`
- Host pipeline `HostStressPipeline` (`model/pipeline.py`): waveform → features → model → detector end-to-end, a host mirror of the Android `StressPipeline.kt`, with an integration test over calm/stressed traces plus unvoiced gating and reset. `b9fe9ad`
- CI workflow running the host pytest suite on every push and PR (uv, Python 3.11, verified pins), plus a guard test that parses the workflow's YAML invariants. Fully offline — no live token. `1c08b03`
- INT8 export of the shipped production recipe (`quantize_production`, PT2E + XNNPACK): a deployable ~12.3 KB INT8 `.pte`. At ~1,549 params the program is overhead-dominated, so INT8 only trims the `.pte` ~5% (versus the ~2.9x seen on the base width); its real win is integer NPU compute with unchanged predictions (scores within ~0.004 of eager). `378a816`
- Real-time guarantee: `realtime_factor()` reports median/max processing time and real-time factor for the waveform → state chain, and `tests/test_latency.py` certifies the README real-time claim against hot-path regressions. `df3b999`
- Reproducibility guarantee: `tests/test_reproducibility.py` asserts two seeded `train_production(seed=0)` runs yield identical validation accuracy, bit-identical weights, and a byte-identical `.pte` despite global-RNG churn between them. `2cb46cc`
- Multi-seed robustness evidence: `robustness_curve(..., eval_seeds=...)` averages accuracy/F1 across several eval seeds and records the per-SNR accuracy **std** (`acc_std`). `build_production` now ships the production record averaged over 5 eval seeds, so the advertised floors carry a spread (e.g. 0 dB = 0.842 ± 0.015) instead of resting on one lucky draw. `n_eval_seeds=1` keeps the fast single-seed path.
- INT8↔fp32 robustness comparison (`model/int8_robustness.py`): runs the noise sweep through both the eager fp32 model and the shipped INT8 `.pte` (via the ExecuTorch host runtime) on *identical* inputs, and reports a paired per-SNR accuracy gap plus a verdict. The deployable INT8 model **preserves the fp32 floor** — reliable down to 0 dB with a worst-case −0.008 accuracy delta — so "INT8 on the NPU" holds under noise, not just on clean audio. Recorded in `docs/benchmarks/int8_robustness.{json,md}` and rolled into the index.
- Colored-noise robustness (`model/noise_colors.py`): the SNR sweep gained a `noise_color` (`white`/`pink`/`brown`) so robustness can be measured against realistic acoustic spectra, not just flat white noise. White turns out to be the *worst case* — pink and brown (energy concentrated in low frequencies, away from the discriminative mel bands) hold as well or better, with the floor holding to −5 dB for brown — so the advertised white-noise floor is conservative. The default stays `white`, byte-identical to prior records. Recorded in `docs/benchmarks/noise_colors.{json,md}`.
- Cross-initialization robustness envelope (`model/init_envelope.py`): trains several independent inits of the shipped width and runs each through the same noise sweep, then derives the **conservative envelope** — the least-noisy per-init reliable floor, the SNR every init still clears regardless of the training seed. This is the evidence behind the README's "10 dB is the envelope we stand on": across 5 inits, four hold to 0 dB but one only to 10 dB, so the honest cross-init floor is 10 dB even though a typical init does better. Complements the eval-seed averaging (which varies the eval draw with the model fixed) by measuring variance across the *weights*. Recorded in `docs/benchmarks/init_envelope.{json,md}` and rolled into the index.
- Recipe-parameterized cross-initialization envelope (`model/recipe_envelope.py`): the augmentation-recipe A/B found, on a *single* seed, that training on lower SNRs deepens the reliable floor (none → 10 → 0 → −5 dB) — but flagged that below 10 dB stays init-sensitive, leaving the README's cross-init envelope claim "unchanged pending a multi-init confirmation." This **is** that confirmation: for each recipe it trains several independent inits, runs each through the same noise sweep, and reduces them to the conservative envelope (reusing `init_envelope`). The result settles the envelope-vs-floor question honestly — the **`aggressive`** recipe `{clean,20,10,5,0,−5}` moves the cross-init envelope from **10 dB → 0 dB across 4 inits** at no clean-accuracy cost (both hold mean clean acc 1.000). So the production floor genuinely *can* be pushed below the prior 10 dB envelope by training on lower SNRs — a real cross-init gain, not one lucky seed; the single-seed −5 dB floor does not fully survive at the envelope level (the envelope lands at 0 dB, the SNR *every* init clears). Recorded in `docs/benchmarks/recipe_envelope.{json,md}` and rolled into the index.
- Noise-augmentation recipe A/B (`model/augmentation_ab.py`): the detector A/B established that the lever for the noise floor is *training*, not detector knobs — so this sweeps the training-noise recipe itself. Each recipe is a pool of training-time SNRs (gentle `{clean,20,10}` → aggressive `{clean,20,10,5,0,-5}`); all share architecture, epochs, optimizer, and the *same* eval draw, so the floor gap is the recipe's. The result is **monotone and free**: the reliable floor deepens with augmentation aggressiveness — none (clean-only) → 10 dB (mild) → 0 dB (moderate) → **−5 dB (aggressive)** — at **no clean-accuracy cost** (every recipe holds clean acc 1.000). The harness recommends the deepest-floor recipe that keeps clean accuracy above a configurable bar. This is single-seed evidence that the production floor can be pushed below the 10 dB cross-init envelope by training on lower SNRs; below 10 dB remains init-sensitive (see the cross-initialization envelope), so the envelope claim is unchanged pending a multi-init confirmation. Recorded in `docs/benchmarks/augmentation_ab.{json,md}` and rolled into the index.
- Detector A/B in the noise regime (`model/detector_noise_ab.py`): the failure-mode and detector-robustness findings together suggested a fix — since the model goes *silent* under noise (it doesn't cry wolf), a lower stress threshold / faster attack might recover detections below the 10 dB floor cheaply. This harness tests that by running the shipped model and the *same* noisy traces through the `detector_robustness` sweep once per candidate config, and recommends the one that pushes the detection floor deepest into noise while keeping worst-case false alarms within budget. **The hypothesis is refuted:** lowering the threshold (0.6 → 0.5/0.45) does raise mean detection (0.54 → 0.67) but the worst-case false-alarm rate jumps from 0.03 to 0.31–0.84, and the end-to-end floor gets *worse* (10 dB → 20 dB) because the same noise that hides stress trips false alarms once the bar drops. The **default (stress=0.6, release=0.45, alpha=0.4) is the best operating point under noise** — the 10 dB floor is fundamental to the model, not a detector-tuning artifact, so the real lever is noise-augmented *training*, not knob-twiddling. Recorded in `docs/benchmarks/detector_noise_ab.{json,md}` and rolled into the index.
- End-to-end detector robustness under noise (`model/detector_robustness.py`): the prior noise work scored the *raw model* one window at a time, but the product ships the **detector** — EMA smoothing + dual-threshold hysteresis over a *stream* of windows. This harness streams multi-window noisy traces through `HostStressPipeline` (a fresh detector per trace) and reports, per SNR, the **detection rate** on stressed traces, the **false-alarm rate** on calm ones, and the **median windows-to-latch**, then names the lowest SNR still meeting the detect/false-alarm target — the end-to-end *detection floor*. The shipped detector latches clean and 20/10 dB stress on the first window with zero false alarms and holds its **detection floor at 10 dB**, matching the cross-init envelope; below it the decision goes **silent** (detect rate → 0 by −5 dB) rather than crying wolf — smoothing buys stability but cannot recover information the model has already lost. Recorded in `docs/benchmarks/detector_robustness.{json,md}` and rolled into the index.
- Failure-mode breakdown under noise (`model/noise_failure_mode.py`): the same SNR sweep split by error *direction* — precision/recall plus whether the model **misses stress** (false negatives, the detector goes silent) or **false-alarms** (false positives, it cries wolf), naming the dominant failure at the first sub-threshold SNR. The production model degrades by going **silent**: as noise rises it collapses toward predicting "calm" (recall → 0 by −5 dB), it does not cry wolf — which tells the detector gate to favour a lower stress threshold / faster attack in noisy regimes rather than more smoothing. Recorded in `docs/benchmarks/noise_failure_mode.{json,md}` and rolled into the index.
- INT8 calibration A/B (`model/int8_calib_ab.py`): PT2E static quantization picks its integer scales from a *calibration* batch, and the shipped INT8 `.pte` calibrates on **clean** audio even though the model trains noise-augmented and runs on noisy on-device audio — so this asks whether matching the calibration distribution to deployment preserves the noise floor any better. It quantizes the *same* trained model two ways (clean vs noise-augmented calibration drawn from the training SNR pool `DEFAULT_AUG_SNRS`) and sweeps both INT8 runtimes plus eager fp32 over *identical* noisy inputs, reporting per-calibration reliable floor and per-SNR INT8−fp32 gap. **Result is a clean null: no difference** — both calibrations hold the **-5 dB** floor with a mean |Δ| of **0.000** vs fp32 (INT8 predictions are identical across calibration sets). At ~1,549 params the quantizer's per-channel scales already cover the noisy activations, so the simpler clean calibration is sufficient — this *validates* the current `quantize_production` clean-calibration choice with evidence rather than leaving it an untested assumption. Recorded in `docs/benchmarks/int8_calib_ab.{json,md}` and rolled into the index.
- End-to-end latency & Real-Time Factor (`model/latency_rtf.py`): the existing host benchmark times only the model forward pass on a *precomputed* feature tensor, but the always-on product claim is "real-time, offline, on-device" — every **1 s** hop a fresh **3 s** window must become a score before the next arrives, and that budget includes the **log-mel feature extraction**, not just inference. This times the full `PCM → log-mel → score` chain per window for each backend (eager fp32, fp32 `.pte`, INT8 `.pte`), decomposes feature-extraction vs inference cost, and reports the Real-Time Factor against both the window and the streaming hop. The chain runs in **~0.6 ms/window** (fastest `pte-fp32`) against the 1000 ms hop budget — **~1700× real-time head-room**, all backends clear it. The notable finding: on the `.pte` backends the **log-mel front-end is now the larger cost** (≈0.35 ms feature vs ≈0.24 ms inference), so the practical optimization lever for this 1,549-param net is the feature extractor, not the model — and the NPU only widens the head-room from here. Recorded in `docs/benchmarks/latency_rtf.{json,md}` and rolled into the index.
- Score calibration analysis (`model/calibration.py`): StressNet emits `sigmoid(logit)` and the detector gates on `STRESS_THRESHOLD = 0.6`, but a threshold on a *score* only means something if the score is a calibrated *probability*. This measures Expected/Max Calibration Error, the Brier score, a per-bin reliability table, and one-parameter temperature scaling over the noise sweep (where scores spread, unlike the near-deterministic clean set), then renders a verdict. **Finding: the model is under-confident** (ECE **0.242**, signed gap **−0.242**) — windows scored ~0.57 are actually correct **95.6%** of the time; the scores hedge toward 0.5 even when right. So the raw **0.6 gate is conservative**: by the time a score reaches 0.6 the window is essentially always stressed (accuracy 1.000 in the 0.6–0.7 bin, empirical stress rate 0.926 at the gate), and temperature scaling at **T=0.41** sharpens the scores to cut ECE to **0.102**. This does *not* license a blanket threshold drop — the detector A/B showed lowering the gate trips false alarms in the worst-case noise tail — but it documents that the scores understate certainty and that temperature scaling is the clean recalibration lever if probability-meaningful scores are needed (e.g. a confidence meter). Recorded in `docs/benchmarks/calibration.{json,md}` and rolled into the index.

### Changed

- **Promoted the very-aggressive augmentation recipe to production, moving the advertised cross-init envelope from 0 dB to -5 dB at no clean-accuracy cost — and pinned the floor of the augmentation approach.** `DEFAULT_AUG_SNRS` (the pool every shipped model trains on, via `train_production` → `noise_augmented_dataset`) gained a `-10` dB window: `(None, 20, 10, 5, 0, -5)` → `(None, 20, 10, 5, 0, -5, -10)`. The recipe-parameterized cross-init envelope (`model/recipe_envelope.py`, now a three-way ladder `aggressive` → `very-aggressive` → `extreme`) is the evidence — across 5 independent inits the very-aggressive recipe holds a **-5 dB conservative envelope** (three inits reliable to -5 dB, two deeper to -10 dB; all clean acc 1.000) where the prior `aggressive` recipe pinned the envelope at 0 dB, **and** going one notch deeper (`extreme`, adds -15 dB training) does *not* move the envelope further (also -5 dB) — so **-5 dB is the floor of this augmentation approach** and -10 dB is the deepest window worth training on. Every production-derived artifact was regenerated and is internally consistent with the -5 dB envelope: `production` reliable to -5 dB (1.000 ± 0.000 through -5 dB); `init_envelope` envelope -5 dB; `int8_robustness` fp32 **and** INT8 reliable to -5 dB (INT8 still preserves the floor); `noise_colors` -5 dB across white/pink/brown; `detector_robustness` end-to-end detection floor now **-10 dB**. The README headline, `model/production.py`, and the `init_envelope`/`detector_noise_ab` docstrings were updated from 0 dB to -5 dB. **Two notable downstream flips:** (1) `noise_failure_mode` no longer fails by going *silent* — the robust model holds balanced through its -5 dB envelope and, only past it, **inverts to false alarms** (recall stays ~1.0, precision collapses near -15 dB); its sweep was extended to -20 dB to capture this, and the implied gate mitigation at extreme SNR flips to *more* smoothing / a higher threshold rather than a faster attack. (2) `detector_noise_ab` now recommends the `lower-threshold` config holding the detection floor to **-10 dB** at a worst-case false-alarm rate well inside budget (≈0.06, no longer exactly zero) — the more sensitive gate still wins because the robust model isn't crying wolf inside its envelope.
- **Promoted the aggressive augmentation recipe to production, moving the advertised cross-init envelope from 10 dB to 0 dB at no clean-accuracy cost.** `DEFAULT_AUG_SNRS` (the pool every shipped model trains on, via `train_production` → `noise_augmented_dataset`) gained `0` and `-5` dB windows: `(None, 20, 10, 5)` → `(None, 20, 10, 5, 0, -5)`. The recipe-parameterized cross-init envelope (`model/recipe_envelope.py`) is the evidence — across 5 independent inits the aggressive recipe holds a **0 dB conservative envelope** (four inits reliable to -5 dB, one to 0 dB; all clean acc 1.000) where the prior recipe pinned the envelope at 10 dB. Every production-derived artifact was regenerated against the new recipe and is now internally consistent with the 0 dB envelope: `production` reliable to -5 dB (1.000 ± 0.000 at every tested SNR through -5 dB); `init_envelope` envelope 0 dB; `int8_robustness` fp32 **and** INT8 reliable to -5 dB (INT8 still preserves the floor); `noise_colors` -5 dB across white/pink/brown; `detector_robustness` end-to-end detection floor -5 dB; `noise_failure_mode` still degrades by going *silent*, now first sub-threshold at -10 dB. The README headline, `model/production.py`, and the `init_envelope`/`detector_noise_ab` docstrings were updated from 10 dB to 0 dB. **Notable downstream flip:** on the brittle 10-dB-recipe model the detector-knob A/B (`detector_noise_ab`) *refuted* lowering the stress threshold (noise tripped false alarms); on the robust production model every config now holds the -5 dB floor at **zero** false alarms, so the harness recommends the more sensitive `lower-threshold` config — once the model is robust, the knobs are free to be more sensitive. Below 10 dB a net this small is init-sensitive, so 10 dB is the claim we stand on. `c29a359`
